# 演示前人工测试清单（照做即可，全程约 30 分钟）

> 目的：向客户演示前，自己先按本清单走一遍，确保每个客户关心的场景都不翻车。
> 用法：每条照"操作"做，对照"预期"看结果。任何一条不符，先看"翻车了怎么办"。
> 对话类指令一律在 MCP 客户端（Reasonix / Kimi Code / Claude Code 等，已接入 data-engine/mcp_server.py）发送；Web 控制台（:3000）只有管理界面（控制台/表设计/数据源/权限/设置），没有聊天页。
> 高危操作（建库等）会在 MCP 通道挂起：到控制台「权限」页顶部"待审批"区点"批准执行"后才会真正执行。
> 标记：⭐ = 客户最感兴趣的招牌场景（演示必演）

---

## 第 0 步：演示环境自检（2 分钟）

| #   | 操作                    | 预期                          |
| --- | --------------------- | --------------------------- |
| 0.1 | 双击启动应用（启动器）           | 30~60 秒内浏览器自动打开控制台（根路径重定向到表设计器） |
| 0.2 | 看首屏                   | 表设计器画布正常加载（表卡片及连线），无报错弹窗  |
| 0.3 | 左侧栏依次点 控制台/表设计/数据源/设置 | 四个页面都能打开、无白屏无报错             |

> **翻车了怎么办**：某页白屏 → 重启应用再看；端口起不来 → 检查 2025/3000 是否被占用（:2024 已无独立编排服务）。

---

## 第 1 步：⭐ 一句话建数据库（约 5 分钟，最能打动客户）

| #   | 操作                                                             | 预期                                          |
| --- | -------------------------------------------------------------- | ------------------------------------------- |
| 1.1 | 在 MCP 客户端输入：`我想创建一个 图书借阅 行业的数据库，管理图书、读者和借阅记录` 发送                | 10~30 秒 AI 给出设计的表结构提案（含字段与外键）               |
| 1.2 | 在 MCP 客户端回复：`图书表再加一个 ISBN 字段`                                  | 几十秒后 AI 重新给出设计，多了 ISBN                      |
| 1.3 | 确认设计后让 AI 执行建库；打开控制台 → 左侧"权限" → 顶部"待审批"区，点 **批准执行**            | 提示"建库执行汇报：建表成功 3 张"（待实测）                     |
| 1.4 | 控制台左侧点"表设计"                                                    | 画布上能看到新建的 3 张表卡片及连线                         |

> **讲解点**："表结构不是 AI 直接拍的，是**人审确认后**才建的——批准动作就在控制台权限页的待审批区，这是我们和别家最大的区别（白盒）。"
> **翻车了怎么办**：MCP 客户端超过 60 秒无提案 → 检查 MCP 客户端与 mcp_server.py 的连接及 AI 服务配置；待审批区没有条目 → 确认已让 AI 发起建表执行（仅文字提案不会挂起）；建完表画布空 → 点"整理布局"。

---

## 第 2 步：⭐ 文件变数据库（约 8 分钟，核心业务流）

| #   | 操作                                              | 预期                                      |
| --- | ----------------------------------------------- | --------------------------------------- |
| 2.1 | 把定额 PDF 放入 `data-engine/uploads/`（如湖北省定额，可先用小页数段），在 MCP 客户端发送：`把 uploads/ 下 <文件名> 这份文件里的定额项目和材料价格录进库` | 出现进度，开始分批入库                             |
| 2.2 | 等待执行完成，看 AI 汇总回复                                | 最终出**入库报告**：批次数、各表 +N 条、冲突/未映射如实列出     |
| 2.3 | 报告里若有"未映射项"，在 MCP 客户端回复：`1对 2忽略`（或按其提示逐项回）    | 系统按你的确认存档映射规则                           |
| 2.4 | （有扫描件的话）把扫描版 PDF 放入 uploads/ 再发同样指令（换文件名）       | 同样入库成功（**OCR 自动识别，无需任何说明**）             |
| 2.5 | 把同一份文件**再发一遍同样指令**                              | 报告"冲突 N 条"，**主表零新增**（幂等不重复）             |

> **讲解点**："表格进关系库、文字进向量库自动分流；转置表、跨页表都能认；认不出的如实问你，不瞎猜。"
> **翻车了怎么办**：报告出现"操作失败/系统性错误"→ 别演这条，先查 data-engine/logs/ 与 backend.log；扫描件/图片入库无反应 → 检查 OCR_API_TOKEN 是否配置。

---

## 第 3 步：⭐ 自然语言查数据（约 5 分钟）

依次在 MCP 客户端（建议新会话）发送以下问句，对照预期：

| #   | 问句                        | 预期                           |
| --- | ------------------------- | ---------------------------- |
| 3.1 | `现在数据库里有哪些表？`             | 列出全部表+字段+外键关系                |
| 3.2 | `quota_items 有多少条记录？`     | 精确数字（与入库报告一致）                |
| 3.3 | `统计各类材料的平均单价，按单价降序`       | 聚合统计表                        |
| 3.4 | `查询每条主表记录对应的明细数据`         | **主表+材料明细联查表**（A1 编码 + 材料名称） |
| 3.5 | `上传的定额文档里，砌筑工程的工作内容讲了什么？` | 命中原文（向量检索，带来源页码）             |

> **讲解点**："不是 AI 写 SQL，是确定性路由到 28 个原子操作——每次查询都可追踪（看 trace id）。"
> **翻车了怎么办**：某题答非所问 → 换更明确的说法（如加上表名）；3.4 返空 → 确认材料表有数据（控制台看 quota_materials 行数）。

## 第 4 步：数据维护——增删改查 + ⭐ 安全拦截（约 5 分钟）

| #   | 操作                                                                       | 预期                       |
| --- | ------------------------------------------------------------------------ | ------------------------ |
| 4.1 | `往 quota_items 插入一条记录：quota_code=DEMO-001，quota_name=演示墙，base_price=100` | "已插入"，控制台 → 表数据页能查到      |
| 4.2 | `把 DEMO-001 的 base_price 改成 200`                                         | "已更新 1 条"                |
| 4.3 | `往 quota_items 批量插入 2 条：DEMO-002（演示墙A，基价50）和 DEMO-003（演示墙B，基价60）`        | 2 条都入库                   |
| 4.4 | ⭐ `把 DEMO-001 的 id 改成 99999`                                             | **被阻止："id 是系统主键，不允许修改"** |
| 4.5 | `删除 quota_items 中 quota_code 是 DEMO-001 的记录`                             | 删除成功                     |
| 4.6 | ⭐ `查询 quota_code 是 DEMO-002 或 DEMO-003 的记录`，然后 `删除查询到的这些记录`              | 先查出 2 条成选择集，再整批删除        |

> **讲解点**："主键、唯一键、外键、类型全部契约保护——AI 也破坏不了数据纪律。"
> **翻车了怎么办**：改/删报"请先查询"→ 先说一句查询再操作（选择集机制）；4.3 有一条没进 → 看回复里哪条及原因。

## 第 6 步：⭐ 权限与数据治理（约 4 分钟）

| #   | 操作                                                                                       | 预期                       |
| --- | ---------------------------------------------------------------------------------------- | ------------------------ |
| 6.1 | 说明场景（口头）："客户有个乱库想只读迁移"                                                                   | —                        |
| 6.2 | 控制台 → 左侧"权限" → "数据源规则"页签：勾选 primary 的**禁止插入/禁止修改/禁止删除** → 点右上"保存并生效"                   | 提示已保存并立即生效（无需重启）         |
| 6.3 | 在 MCP 客户端发送：`往 quota_items 插入一条记录：quota_code=DEMO-X，quota_name=权限测试`                      | **被拦截："权限不足，禁止 insert"** |
| 6.4 | 在 MCP 客户端发送：`quota_items 有多少条记录？`                                                         | 查询正常（只禁了写）               |
| 6.5 | 权限页取消刚才的勾选 → 保存并生效 → 再发 6.3 的插入                                                            | 插入成功（最后记得删掉 DEMO-X）      |

> **讲解点**："每个库的每张表每种操作都能独立控权——老库只读、新库治理，数据安全可审计。"
> **翻车了怎么办**：拦截没生效 → 确认点了"保存并生效"，用权限页顶部"规则测试"干跑一条验证；恢复后仍拦截 → 确认勾选已取消并再次保存。

## 第 7 步：异常与诚实性（约 2 分钟，可选但加分）

| #   | 操作                      | 预期                   |
| --- | ----------------------- | -------------------- |
